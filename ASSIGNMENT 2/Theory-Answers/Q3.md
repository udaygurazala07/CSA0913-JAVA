## 1. Problem Context & The Junior Developer's Bug
A college fest records attendance by scanning student ID cards across multiple entry gates. Because students may pass through multiple gates, the organizers store scans in a `HashSet<Student>` to de-duplicate scans and retain only unique attendees.

A junior developer implemented the following `Student` class:
```java
class Student {
    String regNo; String name;
    Student(String regNo, String name) { this.regNo = regNo; this.name = name; }
    public boolean equals(Object o) {
        if (!(o instanceof Student)) return false;
        return regNo.equals(((Student) o).regNo);
    }
    // hashCode() is NOT overridden!
}
```

When two distinct `Student` objects with identical registration numbers (`"192311001"`) were scanned at Gate 1 and Gate 3, `HashSet.size()` reported **3** instead of **2**.

## 2. The Formal hashCode–equals Contract in Java

Java's language specification establishes three binding rules governing `equals()` and `hashCode()` in `java.lang.Object`:

1. **Internal Consistency:** Whenever invoked on the same object more than once during an application execution, `hashCode()` must consistently return the same integer, provided no fields evaluated in `equals()` have been modified.
2. **Equality Implies Identical Hash:** **If `a.equals(b)` evaluates to `true`, then `a.hashCode()` and `b.hashCode()` MUST produce the exact same integer value.**
3. **Collision Tolerance:** If `a.hashCode() == b.hashCode()`, `a.equals(b)` is *not* required to be `true` (this represents a hash collision, resolved internally by bucket chaining or treeifying). However, distinct hash codes for unequal objects enhance hash table performance.

> [!CAUTION]
> **Contract Violation:** If a developer overrides `equals()` without overriding `hashCode()`, rule #2 is violated. Two logically equal objects will produce different hash codes, completely breaking all hash-based collections (`HashSet`, `HashMap`, `LinkedHashSet`).

## 3. How HashSet Internally Locates and De-Duplicates Elements

`HashSet<E>` is implemented internally as a wrapper around a `HashMap<E, Object>`:
1. When `set.add(e)` is called, Java computes the 32-bit hash code:
   $$\text{hash} = \text{key.hashCode()} \oplus (\text{key.hashCode()} \gg 16)$$
2. It determines the bucket index using bitwise masking:
   $$\text{bucketIndex} = (\text{capacity} - 1) \ \& \ \text{hash}$$
3. It examines the bucket:
   - If the bucket is empty, a new entry is placed at `bucketIndex`.
   - If nodes already exist in that bucket, Java iterates through the bucket chain and checks:
     ```java
     if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
     ```
4. **The Critical Trap:** Java checks `p.hash == hash` **first** as a fast filter. If the two objects have different hash codes, `equals()` is **never even invoked**. The second object is assumed to be distinct and is inserted into a different bucket, resulting in duplicate entries.

## 4. Three Deliberately Designed Experimental Tests

### Test 1: Set of Scans Where HashSet Appears to Work Correctly
- **Scenario:** The same student reference `s1` is passed twice:
  ```java
  StudentUnfixed s1 = new StudentUnfixed("192311001", "Arun");
  set.add(s1); // Gate 1
  set.add(new StudentUnfixed("192311002", "Divya")); // Gate 2
  set.add(s1); // Gate 3 (passing same reference s1)
  ```
- **Prediction:** Size = **2**.
- **Reason:** In `HashMap.putVal()`, Java checks reference identity: `(k = p.key) == key`. Because `s1 == s1` is true and their `identityHashCode` matches, the duplicate is successfully detected.
- **Observed Result:** Set size = **2** (Prediction Verified: **True**).

### Test 2: Deliberately Expose Duplicate Entries
- **Scenario:** Two distinct `new` instances with identical `regNo` are scanned:
  ```java
  set.add(new StudentUnfixed("192311001", "Arun"));  // Gate 1
  set.add(new StudentUnfixed("192311002", "Divya")); // Gate 2
  set.add(new StudentUnfixed("192311001", "Arun"));  // Gate 3 (new instance)
  ```
- **Prediction:** Size = **3**.
- **Reason:** The two Arun objects have different heap memory addresses. Inherited `Object.hashCode()` computes distinct hashes for each instance. They are routed to different buckets; `equals()` is bypassed entirely.
- **Observed Result:** Set size = **3** (Duplicate admitted! Prediction Verified: **True**).

### Test 3: The Mutable Key Trap (Post-Insertion Field Mutation)
- **Scenario:** An attendee's `regNo` is mutated after being added to the `HashSet`:
  ```java
  MutableStudent ms1 = new MutableStudent("192311001", "Arun");
  set.add(ms1); // Placed in bucket corresponding to hash(192311001)
  ms1.regNo = "192311999"; // Key field mutated!
  ```
- **Prediction:** `set.contains(ms1)` returns `false`, and adding another `"192311999"` student creates a duplicate.
- **Reason:** Mutating `regNo` changes `ms1.hashCode()`. When `contains()` or `remove()` is invoked, Java calculates the new bucket index and searches there. But `ms1` is physically stranded in its original bucket.
- **Observed Result:**
  - Before mutation: `contains(ms1) -> true`
  - After mutation: `contains(ms1) -> false`
  - Set size after re-adding: **2** (creating an unremovable "zombie" duplicate!).

## 6. Alternative Concept & Complexity Analysis

### 6.1 Alternative 1: TreeSet<Student> with Comparator on regNo
- Instead of hashing, `TreeSet` uses a Red-Black balanced binary search tree ordered by `Comparator.comparing(Student::getRegNo)`.
- It defines equality purely based on `comparator.compare(a, b) == 0`. It **never calls `hashCode()` or `equals()`**.
- Guarantees $O(\log n)$ search, insert, and delete. Keeps elements sorted alphabetically by registration number.

### 6.2 Alternative 2: HashMap<String, Student> Keyed by regNo
- The registration number string is used directly as the map key (`map.put(s.getRegNo(), s)`).
- Relies on Java's built-in `String.hashCode()`, which is already immutable and optimized with cached hash values.
- Delivers $O(1)$ average time per scan.

## 7. Best Practice Engineering Rules for Keys
1. **Always Override Both Together:** Whenever `equals()` is overridden, `hashCode()` must be overridden using the exact same subset of identity fields.
2. **Enforce Immutability:** Declare all fields used in `equals()` and `hashCode()` as `private final`. This permanently prevents the post-insertion mutation trap demonstrated in Test 3.
