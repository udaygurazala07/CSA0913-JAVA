## 1. Problem Context & Requirements
A hospital pharmacy manages stock for thousands of pharmaceuticals, each indexed by a unique alphanumeric medicine code (e.g., `MED-004821`). The operational profile consists of two distinct phases:
1. **Daytime Transactional Workload:** Pharmacists and billing terminals query inventory hundreds of thousands of times a day to verify availability and prices during prescription dispensing.
2. **Evening Reporting Workload:** At the end of every operating day, the system must generate two official audit reports:
   - **Report 1 (Catalog Audit):** All medicines sorted alphabetically by **medicine code**.
   - **Report 2 (Intake Log):** All medicines listed in the **exact chronological order they were added** into inventory.

## 2. Before Implementation: Theoretical Cost Analysis

| Map Implementation | Internal Data Structure | `put()` Complexity | `get()` Complexity | Iteration Complexity | Key Ordering Behavior |
| :--- | :--- | :---: | :---: | :---: | :--- |
| **`HashMap<K, V>`** | Hash table (array of buckets + linked lists/Red-Black trees) | $O(1)$ average | **$O(1)$ average** | $O(\text{capacity} + N)$ | Arbitrary / chaotic hash order; changes during rehash |
| **`TreeMap<K, V>`** | Self-balancing Red-Black binary search tree | $O(\log N)$ | $O(\log N)$ | **$O(N)$** | **Natural sorted key order (Code Order)** |
| **`LinkedHashMap<K, V>`**| Hash table + doubly-linked list running through all entries | $O(1)$ average | **$O(1)$ average** | **$O(N)$** | **Preserves exact insertion order (Order Added)** |

### Natural Report Generation vs. Extra Work Needed:
1. **Report 1 (Code Order):**
   - **Naturally produced by:** **`TreeMap`**. Traversing `treeMap.values()` performs an in-order binary tree traversal, yielding code order directly in $O(N)$ time with zero extra memory allocations.
   - **Extra work if using `HashMap` or `LinkedHashMap`:** The map entries must be dumped into an intermediate list and sorted with `list.sort(Comparator.comparing(Medicine::getCode))`, incurring $O(N \log N)$ time and $O(N)$ auxiliary heap memory.
2. **Report 2 (Order Added / Insertion Order):**
   - **Naturally produced by:** **`LinkedHashMap`**. Its internal `before` and `after` pointers link entries in chronological addition sequence. Iterating `linkedHashMap.values()` takes $O(N)$ time.
   - **Extra work if using `HashMap` or `TreeMap`:** Neither structure maintains insertion sequence. To produce this report, the developer must either embed an explicit arrival timestamp/index inside each `Medicine` record and sort the collection at night ($O(N \log N)$), or maintain a separate parallel historical list.

## 4. Scalability Inquiry & Engineering Deployment Decision

### 4.1 Acceptable Response Time Definition
In a hospital pharmacy, stock lookups must provide seamless, non-blocking responsiveness for real-time dispensing terminals, automated dispensing cabinets, and emergency room prescription verification.
- **Engineering Target:** An acceptable response time for an in-memory lookup is **$\le 10$ microseconds ($10,000$ ns)**.
- **Measured Result:** Both `HashMap` (333.6 ns) and `LinkedHashMap` (414.9 ns) operate over **24 times faster** than this threshold. `TreeMap` (1,508 ns) is also well within interactive limits, but is **4.5x slower** than `HashMap` due to tree pointer hopping.

### 4.2 Which Map Would You Deploy?
**Recommendation: Deploy `LinkedHashMap<String, Medicine>`.**
- **Defense:**
  1. **Daytime Lookup Dominance:** Daytime lookups account for 99.9% of system activity. `LinkedHashMap` delivers near-instant $O(1)$ lookups (**414.9 ns** per lookup for 100k items), virtually identical to `HashMap` (333.6 ns).
  2. **Zero-Overhead Intake Report:** `LinkedHashMap` naturally preserves insertion order without any extra arrival indices or sorting algorithms. Generating Report 2 takes only **4.34 ms**.
  3. **Tolerable Batch Nightly Sort:** Generating Report 1 requires extracting and sorting the inventory by code once per night. At 100,000 records, this takes **210 ms**—a negligible one-time batch cost run during off-peak night hours.
- **Where the Remaining Cost Comes From:**
  In `LinkedHashMap`, each entry contains 4 object references (`hash`, `key`, `value`, `next`) plus 2 additional references (`before`, `after`) for the doubly-linked list. The remaining cost comes from this extra 16-byte memory footprint per entry and cache misses when traversing non-contiguous bucket nodes.

### 4.3 Why Hashtable is Not Preferred in Modern Java
1. **Thread Contention:** Every method in `Hashtable` (`get()`, `put()`, `remove()`) is guarded by `synchronized`. Multiple concurrent reader threads block one another, crippling multi-core scalability.
2. **Null Restrictions:** `Hashtable` throws `NullPointerException` on `null` keys or values, whereas modern collections handle them gracefully.
3. **Obsolescence:** Introduced in JDK 1.0, `Hashtable` predates the Java Collection Framework. For thread-safe requirements, modern production architectures use **`ConcurrentHashMap`**, which uses fine-grained bucket striping and lock-free CAS reads.

## 5. Alternative Concept & Complexity Analysis: Sorted Array & binarySearch()

If the inventory were kept in a plain `Medicine[]` array kept sorted by `code`:
- **Lookup:** `Arrays.binarySearch(array, key)` takes $O(\log N)$ time (**1,460 ns**).
- **Report 1 (Code Order):** $O(N)$ trivial sequential scan (already sorted).
- **Insertion (`put`):** Inserting a new medicine requires finding the insertion point and shifting all subsequent elements using `System.arraycopy()`, taking **$O(N)$ time**. For 100,000 medicines, inserting just 1,000 items takes hundreds of milliseconds of CPU memory copying.
- **Space:** Most compact ($N$ references, zero wrapper node overhead).

### Complexity Comparison
| Feature | `HashMap` | `TreeMap` | `LinkedHashMap` | Sorted Array (`binarySearch`) |
| :--- | :---: | :---: | :---: | :---: |
| **Lookup (`get`)** | **$O(1)$** | $O(\log N)$ | **$O(1)$** | $O(\log N)$ |
| **Insertion (`put`)** | **$O(1)$** | $O(\log N)$ | **$O(1)$** | **$O(N)$ (Fatal Flaw)** |
| **Code-Order Report** | $O(N \log N)$ | **$O(N)$ (Natural)** | $O(N \log N)$ | **$O(N)$ (Natural)** |
| **Insertion-Order Report** | Not Supported | Not Supported | **$O(N)$ (Natural)** | Not Supported |
| **Space Overhead** | Medium ($1 \times \text{Node}$) | High ($1 \times \text{TreeNode}$) | Medium-High ($1 \times \text{Entry}$) | **Lowest ($1 \times \text{Array slot}$)** |

### Conclusion on Sorted Array
While a sorted array offers optimal cache locality for static read-only tables, its $O(N)$ insertion cost makes it completely unacceptable for an active pharmacy where new medicine shipments and stock batches arrive continuously. `LinkedHashMap` remains the ideal engineering solution.
